## Workflow

1. **Reverse-engineer the reference site first** (if cloning an existing tool): download the HTML, CSS, and shipped JS bundle; inventory both API paths and user-facing behavior. Grep for `/api/`, `EventSource`, `WebSocket`, provider names (alchemy/reservoir/opensea/seadrop/rpc.*), plus UI hooks such as `data-*`, `localStorage`, alert labels, time-window constants, wallet methods, filters, empty/error states, and translation dictionaries. Probe representative endpoints and identify which data is first-party vs. third-party. Build an evidence matrix with four confidence classes: **live-UI observed**, **bundle-confirmed**, **live-API confirmed**, and **inferred/unexercised**. Inventory every control, displayed field, state, alert, validation rule, persistence behavior, empty/error state, and interaction—not just headline features. Do not infer feature parity from endpoint names alone: MintGo's bundle exposed wallet monitoring, threshold/sound alerts, blocklists, mint execution, unit switches, and timing windows that were not obvious from its landing HTML. MintGo's "upcoming mints" turned out to be on-chain SeaDrop configs enriched with OpenSea metadata—not a secret calendar API. Read `references/mintgo-reverse-engineering.md` for the endpoint/UI inventory and `references/mintgo-multichain-architecture-2026-08.md` for same-origin cookies, SSE cursor/replay, Ethereum/Robinhood RPC pools and cadence, Robinhood SeaDrop evidence, utility-NFT filtering, and the independent persistent-indexer shape. For same-origin session gates, POST `/api/session` with browser-like `Origin`, `Referer`, `Sec-Fetch-*`, and UA headers, then reuse a real cookie jar for **both reads and writes** on every request (`curl -b jar -c jar`) because protected responses may rotate the access cookie.
2. **Public RPC layer** — see pitfalls for provider limits. Pattern: ordered failover list, 6s AbortController timeout, batched JSON-RPC, single-error-object batch responses must be handled, send `user-agent: Mozilla/5.0` (some providers 403 without it).
3. **Mint activity**: fetch only mints at the RPC level with a position-specific topic filter, not all transfers. The zero address in a topic is a 32-byte word — pass `0x` + 64 zeros (a 40-hex `0x0000…0000` address is rejected as invalid params). ERC-721 mints: `topics: [TransferTopic, ZERO_WORD]` (from = topics[1]). ERC-1155 mints need a second call because from = topics[2] (topics[1] is operator): `topics: [[SingleTopic, BatchTopic], null, ZERO_WORD]`. A mint-only filter returns only from-zero transfers (~1.6 mints/block on Robinhood vs ~15 transfers/block), so the same window yields ~10× more mints per `eth_getLogs` call and stays under provider/budget limits. Still require **exactly 4 topics** on decode (3 topics = ERC-20 `Transfer`, which shares the ERC-721 topic0 but has no tokenId — filter it out). For a Cloudflare-Workers indexer, see `references/cloudflare-worker-evm-indexer.md` (subrequest/write budgets incl. Workers Paid D1 pricing and the delete-as-write retention trap, RPC failover, block-time estimation instead of per-block getBlock, `eth_getLogs` 1000-block range cap, sampling, FK-driven write amplification, and the aggregate-forward full-coverage design).
4. **Upcoming mints (SeaDrop)**: query canonical SeaDrop address for `PublicDropUpdated` logs; topic0 = `0x8764214b5defe9caa9c5b38b36f0cc5e482a8ab15d78696659e61989e48e6e70`; topic[1] is the NFT contract; data = 6 ABI words (mintPrice, startTime, endTime, maxPerWallet, feeBps, restrictFeeRecipients). Keep the latest update per contract (per chain/contract, by block/log order). Zeroed fields are protocol defaults: price 0 = free, maxPerWallet 0 = unlimited, missing times = unknown. See `references/seadrop-schedule-parity.md` for the verified decoder, three-state classifications (free/paid/unknown, limited/unlimited/unknown), UTC status boundaries, seven-day horizon semantics, ten-minute cache/route contract, the TS BigInt-literal pitfall, and the SC-11/SC-12 schedule-alert + stage-lifecycle transition engine (deterministic-clock pattern, emit-once-per-version dedupe, supersede/cancel/end semantics).
5. **Multi-chain expansion (Ethereum → Robinhood → Base)**: preserve one normalized event model, but configure RPCs, explorers, native units, marketplace enrichment, lookback sizes, and utility-NFT exclusions per chain. Confirm a chain with direct `eth_chainId`, `eth_blockNumber`, and bounded Transfer-from-zero `eth_getLogs` probes before exposing it. Prefix record IDs with the chain (`robinhood:0x…`) to prevent address collisions. Robinhood activity includes position, LP, vote-escrow, credential, SBT, and other utility NFTs; build chain-specific contract/keyword exclusions and manually sample surviving contracts before calling the feed collectible-mint intelligence. Never infer SeaDrop addresses, marketplace coverage, or mint-factory equivalence from Ethereum—verify each through chain logs or authoritative deployment records. See `references/robinhood-chain-nft-mint-data.md` for verified infrastructure, SeaDrop, and enrichment details.
6. **Metadata**: batched `eth_call` for name/symbol/totalSupply; decode dynamic strings AND bytes32 fallback; non-standard contracts get address-derived labels, never crash.
6. **OpenSea enrichment (optional, best-effort)**: fetch `https://opensea.io/contract/ethereum/<address>` (redirects to /collection/<slug>), parse the embedded GraphQL hydration JSON for `collectionBySlug` (name, slug, imageUrl, verified, drop.stages, stats). See pitfalls — the page has MULTIPLE fragments.
7. **Serverless/Vercel feed design**: bounded lookbacks, in-memory cache (25s) + s-maxage headers, last-known/demo modes marked `degraded: true`, explicit provenance on every record, never fabricate live data. `demoFeed()` returns empty arrays + error, not fixtures.
8. **Production data acceptance is semantic, not transport-only**: after deployment, verify more than HTTP 200 and schema validity. Assert that expected live sections contain records when the source should be active, inspect representative values/provenance, and confirm the rendered page actually exposes those records. A private upstream can return HTTP 200 with structurally valid but empty payloads; do not label collection/trending endpoints `healthy` merely because JSON parsing succeeded. Treat unexpected empty payloads as degraded/unavailable and fail the delivery gate rather than shipping an attractive empty shell. Prefer the independent bounded public-RPC pipeline when the private source cannot prove usable data.
9. **Browser QA**: screenshot the built app desktop + mobile before deploy (Playwright pitfalls below), then vision-check.
10. **Read-only wallet review**: cross-check live native balance and nonce through at least two public RPCs, then use the explorer address page for account age, recent activity, token/NFT inventory, and multichain valuation. Separate economically valued holdings from spam/dust. For project allowlists, distinguish a previously verified registration receipt from current membership; only the project’s live API, mint contract, or current Merkle proof can establish present eligibility. See `references/read-only-wallet-and-allowlist-review.md`.
11. **Intraday NFT trade reconstruction**: paginate wallet transactions and NFT transfers, then correlate each relevant receipt with internal transfers and state changes. ## Off-ramp / exchange tracing

When asked "how much did I off-ramp to Coinbase/ChangeNOW/etc.", first lock the requested accounting mode instead of silently narrowing it:

- **Confirmed off-ramp:** only label-verified exchanges and deposit addresses with a defensible forwarding chain.
- **Probable gateway:** include unlabeled one-time/low-activity recipients that rapidly forward nearly the full amount to a consolidation or exchange node; keep this subtotal separate.
- **Gross outbound threshold:** when the user says to count every transfer at/above an amount (for example `$500`, `$550`, `$1,000`) regardless of destination, enumerate every qualifying canonical stablecoin transfer. Do not exclude swaps or ordinary recipients from this gross total; classify them separately so gross outflow is not mislabeled as off-ramping.

Workflow:

1. Filter plain ETH sends: `from == wallet`, value > 0, no functionName, `isError != 1`. Sum by recipient.
2. Analyze ERC-20s separately—native transaction `value` never contains USDC/USDT. Select canonical contracts by chain + contract address + decimals, never by symbol alone. On Ethereum mainnet: USDC `0xA0b86991c6218b36c1d19d4a2e9Eb0cE3606eB48` (6 decimals); USDT `0xdAC17F958D2ee523a2206206994597C13D831ec7` (6 decimals). Symbol-only filtering can count counterfeit/spam tokens.
3. For a user-specified threshold, compare decoded token units (`raw / 10**decimals`) and list every qualifying transfer with date, token, amount, destination, and hash. Report transfer count, unique-address count, per-address totals, and grand total.
4. Discriminate EOA vs contract with ONE batched JSON-RPC `eth_getCode` call. Exchange deposit addresses are usually EOAs; marketplace/swap relays are contracts and must be classified rather than silently discarded in gross-outbound mode.
5. Trace each significant recipient's own `txlist` and `tokentx`. The classic deposit-gateway pattern is wallet → per-user deposit address → labeled hot wallet. Match by token contract and time proximity; do not add the second hop to the user's amount.
6. Detect own-wallet flows: if a recipient sends most funds BACK to the origin wallet, classify it as a likely personal wallet. Exclude it from off-ramp totals, but retain it if the user explicitly requests every outbound transfer.
7. Attribute by the user's direct sent amount, not the forwarded amount (gateways carry multiple users' inflows).
8. Value ETH in historical USD at deposit date with Yahoo daily closes. Stablecoins can be reported at nominal units, noting material depegs if relevant.
9. Present mutually exclusive subtotals: confirmed named exchange; probable/unlabeled gateway; gross non-gateway transfers (swaps, commerce, personal); excluded fake tokens. Respect explicit exchange exclusions such as Binance/KuCoin in both detail and headline totals.

Label discipline: Etherscan address pages contain a "popular labels" sidebar (Coinbase, Gate, etc. on EVERY page) — keyword grep is noise. Only the page `<title>` or a parsed `Public Name Tag` counts as a label. Unlabeled consolidation addresses that receive many small deposits and forward in bulk (ChangeNOW-style) must be reported as "likely exchange, unconfirmed", never silently promoted to confirmed. Never infer that an arbitrary round-number transfer is an exchange deposit merely from its amount; include it only under gross-threshold mode unless routing evidence exists.

Confirmed label addresses from Aug 2026 tracing live in `references/exchange-offramp-tracing.md`. Canonical stablecoin filtering, gross-threshold enumeration, and the distinction between off-ramp versus total outbound accounting live in `references/stablecoin-threshold-accounting.md`. RouteScan `txlistinternal` returns empty for contracts — internal-tx tracing is not available there; fall back to outer-tx traces.

## Pitfalls

- **RPC eth_getLogs range limits vary wildly**: `rpc.mevblocker.io` allows up to 10,000 blocks per call; `eth-mainnet.public.blastapi.io` rejects anything over 10 blocks; **Alchemy Free tier caps at 10 blocks** (PAYG removes it); `ethereum-rpc.publicnode.com` 403s without an address restriction. Chunk ranges per provider and fail over — and make the chunk size a PER-CHAIN/per-provider record, never a global constant (Robinhood arrowrpc 1000 vs Alchemy-free Ethereum 10 in the same worker). **Range violations can masquerade as rate limiting**: arrowrpc answers an over-range getLogs with HTTP **429** + JSON-RPC `-32005 "batch rejected: block range N exceeds max 1000"`. Before spending cycles on pacing/backoff, read the 429 BODY — it may be a query-shape rejection, not a rate limit.
- **Batch responses**: some providers answer a JSON-RPC batch with ONE error object instead of an array — treat non-array as provider failure, not success.
- **OpenSea hydration JSON**: the page contains several `collectionBySlug` fragments (urql rehydrate pushes); the first occurrence may be a partial fragment without `name`/`drop`. Nolan rules: `.lower()` checksums; treat zero-`value` ERC-20 rows as dust; `token-balances` shows aggregated count per NFT collection (not per tokenId). Pace ~0.3s between calls; a 60-wallet sweep runs ~2-3 min.- **RH RPC `eth_getTransactionByHash` batch pacing:** arrowrpc 429s on batches of 50 with no backoff. Keep batches ≤20 and sleep ~0.4s between batches with a small retry (verified 2026-08-17 on 834-tx scan). Also: `eth_getTransactionByHash` on RH returns `value` in wei where mint/sale txs carry the ETH amount — this is the keyless sale-price source on a chain whose Seaport also settles in WETH.**
- **RH RPC 403s urllib without a UA; curl is fine.** Python `urllib` against `rpc.mainnet.chain.robinhood.com` returns 403 unless you send `User-Agent: Mozilla/5.0` (terminal curl works because curl sends its own UA). Always set the UA on Python RPC clients here.
- **Empty `eth_getLogs` ≠ no mints.** Two silent-false-negative traps: (1) `fromBlock` later than the mint date returns `[]` — convert the claimed mint date to a block range first; (2) the queried contract may be a copycat — Blockscout search for a hot name returns 30+ same-named contracts, and only one is canonical. Confirm both the canonical address and a block range that covers the mint window before concluding "no mints / wrong benchmark".
- **A FAILED `eth_getLogs` is not a zero — never report "no volume/no swaps" from a query that errored.** Range/param rejections (HTTP 400) and 429s wipe the result set, and an empty-looking `logs == []` default then reads as negative proof. On PRTSCN/Ink every swap-log chunk returned HTTP 400 and a careless pass printed "TOTAL swaps: 0"; the honest proof came from three successful reads: `addresses/{pair}/transactions` → 0 items, `addresses/{pair}/token-transfers` → only the addLiquidity rows, and `tokens/{token}/counters` + newest-transfer timestamp → no movement for days. Fail over (smaller range, other provider) or use explorer lists; if you cannot get a successful read, say the market state is UNVERIFIED rather than calling it dead.
- **Unverified token, no ABI: name it from its own method IDs, then attribute its flows.** Collect the distinct selectors on every tx/transfer touching the contract, resolve each at `4byte.directory/api/v1/signatures/?hex_signature=0x<sel>`, and group the full transfer list with `Counter((from, method))`. `0x8a8c523c=enableTrading()` + `0x4022b75e=airdropTokens(address,address[],uint256[])` converted an opaque blob into "gated launch token", and the grouping showed 1,260 of 1,263 transfers came from ONE wallet — i.e. the founder pushed the airdrop personally, which is a materially different claim from "a token appeared". Also check `ens_domain_name` on transfer rows (free operator identity) and whether supply divides cleanly by the collection size (444,000,000 = 4,440 × 100,000).
- **Rug surface check: read the PAIR's own holder list, not just the token's.** Find the V2 pair (`getPair`, reserves `0x0902f1ac` — remember token0 may be wrapped native, so "reserve0=0.5" is 0.5 WETH, not ETH), then `tokens/{pair}/holders`. 100% of UNI-V2 parked in the deployer EOA = the whole pool is pullable at will (PRTSCN: 9,423.375 LP unlocked, unburned, deployer EOA with 8 lifetime txs funded 4 minutes before deploy). Then walk the funder's history: a funder that had pulled liquidity from a DIFFERENT token 25 minutes earlier marks a repeatable launch template, not a one-off.
- **Don't copy the reference site's visual design** when asked for "a much better version" — build an original layout (e.g. MintGo's green three-column terminal became a dark-editorial radar) and say so explicitly.
- **Collection name+image enrichment is parity table-stakes; a column labeled "Market" must show MARKET data.** Address-only rows read as "broken" to users (2026-08-14: "no collection names, no images… how is this on parity with the OG?"). Resolve names/images before calling a dashboard done (keyless RH path in `references/opensea-v2-keyless-enrichment.md`). A Market column that shows mint counts reads as "wrong information" — market means volume/change/sales from marketplace events; mint counts belong under a mints/trending label. Per-window switching (1m/5m/10m/30m/1h/…) is core UX, not a nice-to-have. Detail-card dashes also read as broken — populate MINT LIVE (minted/supply + progress), HOLDERS, LATEST, CREATED from the no-key fallback stack (RPC `totalSupply()` + your own all-time minters / first-seen minute) when the explorer is blocked; Blockscout 429s Cloudflare egress, so it can't fill those from a worker. See `references/opensea-v2-keyless-enrichment.md`.
- **Time-based state machines** (alerts, thresholds, windows): pass `nowSeconds` explicitly into pure `advanceX({ state, nowSeconds, ... })` functions instead of `vi.useFakeTimers()`/`Date.now()`; keep `state` JSON-serializable (no Maps/Sets/class instances) so it persists/replays; reject non-monotonic clocks; dedupe emissions per identity/version; use append-only history for lifecycle. Pattern + SC-11/SC-12 detail in `references/seadrop-schedule-parity.md`.

## Pitfalls — cross-collection wallet forensics

- **NEVER value an OpenSea sale event without reading `payment.symbol`.** `int(quantity)/10**decimals` looks like ETH but HoodPepes settles 435 sales in **USDG** (`~$81.52` total) alongside 5,867 ETH and 1,432 WETH sales. Ignoring the symbol turned a wallet's ~$1.07 of stablecoin proceeds into a reported **+1.07 ETH (~$2,640) "biggest winner"** — a fabricated result that survived a full analysis pass. Bucket ETH/WETH into net-ETH and stablecoins into a separate USD column, and name which collections mix denominations. This trap has now fired twice (2026-09-10 and 2026-09-11); treat the symbol check as mandatory plumbing.
- **"Early" must always be defined and labeled, because the definition moves the answer 4x.** On the same four launches: entry-RANK tiers (first 250 minters of each) yielded **0** wallets in 2+ launches; wall-clock first-24h yielded **280**. Rank tiers are silently compressed — DogiHood sold its whole supply in 1.2 h, so "first 250 minters" ≈ the first five minutes. Default to wall-clock first-24h (`mint >= 1 OR buy >= 1`), state the window in the deliverable, and always report the broadest ladder first (ever-touched / 2 / 3 / all) so a short cohort list reads as narrow-by-definition rather than as the whole truth.
- **Same-second mint clustering is NOT evidence of a coordinated ring.** Grouping mints by timestamp produced 6,801 same-second wallet pairs on these launches, but **zero of those pairs recurred in a second launch** — the clusters are the organic public-mint flood (one second contained 752 distinct wallets). Do not present a same-second co-mint graph as a bot-ring finding, and exclude the flood second from burst metrics before calling any wallet a batch-minter.
- **A tight "in all N collections" result is a signal to widen, not to answer.** If the intersection returns ~10 wallets, build the 3-of-N and 2-of-N tiers plus the pattern battery before replying. Emad's correction verbatim: *"i need more than that, there have to be more… find more patterns."*
- **Lead with the list, not the method.** He asked for results "in a list that i can understand" and rejected a methodology-first reply. Numbered wallet lines (address, handle, one-line net) come first; compressed bolded patterns after; full data to an `.xlsx` with one tab per pattern group, referenced by absolute path.
